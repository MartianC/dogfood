# “和狗狗一起吃”记录打卡 Design Concept

**状态：** Design Concept 已收敛，PRD Ready Gate 已批准

**日期：** 2026-07-26

**原始 Brief：** [`docs/superpowers/plans/2026-07-26-shared-meal-checkin.md`](../plans/2026-07-26-shared-meal-checkin.md)

## 1. 原始 Brief 事实

以下内容来自原始 Brief，不把后续推导伪装成用户事实：

- 产品从“浏览狗饭食谱并生成批量制作清单”转向“选择这一顿的人饭菜单，生成可调整的狗饭初稿，完成本餐评估并保存打卡记录”。
- “一起吃”指从人饭菜单中挑选可共用的基础食材，为狗狗单独无调味制作，不是把做完的人饭直接分给狗狗。
- 一次记录只对应一只狗狗。
- 非 `blocked` 目录食材可搜索、添加和自动带入；`blocked` 食材必须阻断并说明原因。
- 初始总量由目标狗狗的本餐能量需求决定；比例不沿用人饭原始分量。
- 食材过少、品类单一或无法满足全部营养目标时仍可生成和保存，不自动补齐食材；不足由本餐评估展示。
- 用户可以调整克重、移除食材，也可以从目录额外添加食材。
- 首版保存的是一条本餐记录，不区分计划与已食用状态。
- 能量与营养密度保持两条独立评估轴。

## 2. 人类澄清

以下内容是本轮塑形中由用户明确确认的决定：

- 核心场景不是偶尔制作鲜食，而是每天与狗狗一起吃；狗狗的大部分主食来自人当天菜单中可共用的基础食材，但必须为狗狗单独烹饪。
- 首版仍只做单餐评估；连续多餐的整体营养情况属于后续能力，首版记录与版本快照应为未来聚合留出余地。
- 多数人饭食材不能覆盖狗饭营养需求。用户预期通过现有本餐评估查看缺口，再使用既有“挑选富含某营养素的食材”入口调整狗饭。
- 首版不新增另一套营养调整推荐能力。
- 首版只从既有人饭菜谱库选择，不提供自定义菜名、自定义人饭原料或搜不到菜时按食材直接开始的兜底。
- 小程序不参与决定用户当天吃什么，也不根据狗狗需求反向规划或推荐人饭菜单。
- 普通营养缺口常驻展示；最高优先级偏高项或关键数据缺失时，保存前确认一次，但仍允许保存。
- `blocked` 食材始终硬阻断，不属于可确认后继续的营养提示。
- 自动生成只服务档案完整、8 周以上、没有疾病或治疗性体重管理需求的犬只；妊娠和哺乳犬使用已有繁殖期营养标准。
- 初始克重采用“保守版 C”：系统自动带入可共用食材并计算本餐能量目标，但不为各食材生成缺少依据的伪精确克重；用户输入初始克重后，可等比例调整整餐并通过现有本餐评估继续修改。

## 3. 问题定义

每天为家人和狗狗分别准备完全独立的菜单，会增加选材、份量计算和营养判断成本。用户已经决定自己当天吃什么，但难以快速判断其中哪些基础食材可以与狗狗共用、这些食材应给狗狗多少，以及还缺少哪些营养。

产品需要把用户已经决定的人饭菜单转化为一份可追溯、可调整的狗饭食材起点，帮助用户按本餐能量目标填写和缩放克重，再用现有单餐评估完成必要调整，同时避免制造“本餐已完整均衡”或“适合长期重复喂养”的承诺。

## 4. 核心体验

```text
选择本次狗狗
  → 搜索并选择已经决定的人饭菜单
  → 查看全部来源原料及可共用状态
  → 自动带入可共用食材并显示本餐能量目标
  → 用户填写各食材初始克重
  → 可选：按能量目标等比例调整整餐
  → 查看本餐能量与营养密度缺口
  → 通过现有富含营养素入口增删食材并调整克重
  → 实时重算，直到用户愿意采用当前方案
  → 按评估结果分级提示后保存本餐记录
```

流程成功不要求所有营养指标都达到参考值，但要求用户能看到仍未解决的缺口、超量项和数据不足，并能明确区分“保存记录”和“营养认可”。

## 5. 设计原则

1. **人饭由人决定。** 产品只接收用户已决定的菜单，不反向规划人的饮食。
2. **共用食材，不共用成品。** 狗饭必须单独称量、单独烹饪，不继承盐、油、酱汁和调味。
3. **评估驱动调整。** 自动带入的食材清单只是起点，填写克重、查看缺口并调整是主流程，而不是异常补救。
4. **事实、策略和操作分层。** 目录身份、安全策略、产品操作资格和营养数据资格不得混为同一字段。
5. **不制造完整均衡承诺。** 标准对照是估算参考，不是对家庭自制单餐或长期饮食的认证。
6. **确定且可追溯。** 相同输入和版本必须得到相同结果；历史记录保留档案、菜单、食材、评估和算法版本快照。
7. **为跨餐聚合留边界，不提前实现。** 首版记录足够支持后续按日或滚动周期聚合，但不输出跨餐结论。

## 6. Research 证据

营养责任边界研究见：

[`docs/superpowers/specs/2026-07-26-shared-meal-nutrition-boundary-research.md`](./2026-07-26-shared-meal-nutrition-boundary-research.md)

研究结论：

- 国标、FEDIAF 和 AAFCO 可作为单餐营养密度参考，但不能直接证明家庭自制单餐或长期饮食完整均衡。
- 长期家庭自制饮食占主要摄入时，应提示用户咨询兽医或兽医营养专业人士。
- 保存记录必须与营养认可分开表达。

## 7. Prototype 证据

### 7.1 问题

仅使用“能量优先、国标与 FEDIAF 等权、营养偏差最小”的目标，能否对常见少量食材生成生活化、非极端且确定性的克重？

### 7.2 方法

- 使用仓库现有 USDA 营养投影、国标与 FEDIAF 标准投影和现有营养评估服务。
- 目标犬只为 10kg、每日 2 餐、一般活动的成年犬；本餐目标约 310 kcal。
- 每种已选食材至少占 5% 的候选质量份额。
- 穷举固定步长的确定性组合，先按目标能量缩放，再比较两套标准的归一化营养偏差。
- 临时运行命令：

```bash
node .tmp/shared-meal-allocation-prototype-cli.js.tmp --all
```

原型代码位于 Git 忽略目录，未进入生产代码，且因未取得 Git 提交许可没有创建技能建议的原型提交。

### 7.3 结果

| 食材组合 | 结果克重 | 能量误差 | 最大食材占比 | 结论 |
| --- | --- | ---: | ---: | --- |
| 仅鸡胸肉 | 鸡胸肉 292g | 0.12% | 100% | 能量可满足，营养缺口大量存在 |
| 仅胡萝卜 | 胡萝卜 646g | 0.01% | 100% | 数学成立，但总量明显不生活化 |
| 鸡胸肉、白米、胡萝卜 | 41g、66g、57g | 0.56% | 40% | 克重较生活化，仍有大量营养缺口 |
| 鸡胸肉、白米、胡萝卜、鸡肝 | 14g、14g、69g、178g | 0.28% | 65% | 营养偏差显著下降，但鸡肝用量形成不可接受的极端解 |

### 7.4 结论

当前 Brief 的“能量优先 + 营养偏差最小”目标不足以直接交付。优化器需要额外的生活化用量约束，否则数学最优解可能放大内脏或其他高营养密度食材。相关约束不是国标或 FEDIAF 自动提供的事实，必须作为版本化产品规则并获得专业依据。

## 8. 可选方向

### 方向 A：无约束营养优化

- 优点：最贴近原始“尽量降低营养偏差”的表述。
- 缺点：已由原型证明会产生极端用量；不适合作为可直接采用的初稿。
- 判断：不建议。

### 方向 B：有生活化边界的确定性优化

- 能量仍为第一优先级。
- 为食材和类别配置有依据、可版本化的最低/最高克重或占比边界。
- 在边界内最小化营养偏差；无法满足时返回受约束的最优结果并如实展示缺口。
- 优点：保留自动调整价值，同时避免明显极端解。
- 代价：需要为边界取得可靠依据，配置与测试复杂度高于原计划。
- 判断：已拒绝。即使配置不写入云数据库，也会形成新的版本化数据契约、专业依据和审核负担；当前没有足够可信的数据支撑这些边界。

### 方向 C：只确定能量目标，由用户建立食材比例

- 系统不使用等质量、等能量或类别启发式规则自动填写单项克重。
- 自动带入可共用食材并显示本餐能量目标；用户输入初始克重后，可复用现有“按目标调整整餐份量”进行等比例缩放。
- 营养标准只用于随后进行的本餐评估，不直接决定食材比例。
- 优点：不新增食材用量配置，不制造“算法已经配平”的错觉。
- 缺点：用户需要先填写各食材的大致克重，初次操作成本高于自动克重方案。
- 判断：已由用户选择，作为首版交付方向。

## 9. 关键权衡

- 自动优化越积极，越需要专业、版本化的用量边界。
- 初稿越保守，用户调整负担越高，但产品承诺越清晰。
- 对单餐保存越宽松，越需要把未解决缺口和长期责任边界持续保留下来。
- 首版不做跨餐评估可以控制范围，但不能宣称单餐评估能够管理每日或长期营养。
