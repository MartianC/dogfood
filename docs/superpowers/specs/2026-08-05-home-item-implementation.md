# 首页体重与护理事项实施交接

**状态：** H2.1 已完成

**日期：** 2026-08-05

**上游：** [`项目结构与界面编排 DAG 路线图`](../plans/2026-08-01-project-structure-and-interface-roadmap.md)

**依赖：** `W1.3`、`C1.3`、`OW1`、`OC1`

## 1. 实现范围

本轮在现有首页“档案事项”结构上扩展体重和护理事项来源，没有重做首页布局，也没有接入统一记录时间轴。首页通过主包只读服务读取两个领域的列表结果，不直读 CloudBase 集合，不新增写入接口或线上资源。

## 2. 数据边界

- 体重只取带合同日期的最新有效测量；旧档案 `weightKg` 不生成首页事项。文案只表达“上次记录于今天/几天前”，不做健康异常判断。
- 护理只取实体中用户明确填写的 `nextDate`，没有日期的记录不生成首页安排。护理卡片主文案使用“计划中的下次「类型」：日期”，狗狗名和用户填写的护理名称放在次级信息中；不推导系统周期、推荐日期或医疗结论。
- 首页状态模型把现有档案完整性/适用性事项与体重、护理事项合并，最多保留三条；既有档案事项保持优先级。
- 体重事项进入带 `dogId` 的体重趋势页，护理事项进入带 `dogId` 的护理记录页，档案事项继续进入档案编辑页。

## 3. 工程映射

| 位置 | 职责 |
| --- | --- |
| `services/homeItemService.js` | 主包只读汇总、体重相对时间、护理分页和事项 view model |
| `services/adapters/cloudbase.js` | 通过 `weightRecord`/`careRecord` 云函数提供列表读取 |
| `services/adapters/mock.js` | 为首页事项提供同形状的本地列表读取 |
| `services/homeStateModel.js` | 合并事项来源、校验展示字段并限制三条 |
| `pages/home/index.js` | 首页生命周期读取、失败降级和事项路由 |
| `pages/home/index.wxml` | 复用原事项卡片和 UI Kernel，仅增加动作绑定 |

## 4. 验证与边界

定向测试覆盖真实记录筛选、护理分页、上海自然日相对时间、三条上限、狗狗归属和三类路由；未执行 CloudBase 部署、集合、索引或线上数据操作。

## 5. H2.2 文案与信息层级调整

2026-08-18 根据首页使用反馈调整，不改变护理记录合同或 `nextDate` 筛选边界：

- 模块标题从事项语义调整为“护理安排”，避免“待处理”带来的紧迫感；
- 有下次日期的护理记录将计划内容放在卡片主标题，例如“计划中的下次「体内驱虫」：9月18日”；
- 狗狗名和用户填写的护理名称保留在次级信息中，多狗场景仍能识别归属；
- 加载、失败和空态统一使用“护理安排”“暂无体重或护理安排”等平缓文案。

## 6. H2.3 主任务卡文案层级调整

2026-08-18 根据首页截图反馈调整，不改变主任务路由或记餐入口：

- 眉题从“当前主任务”调整为“接下来”，减少产品内部术语感；
- 主标题与按钮文案拆分，主标题表达意图（如“准备下一顿”），按钮表达动作（“记一顿”）；
- 今天已有记录时主标题提示“准备下一顿”，并在说明中保留已记录次数；今天暂无记录时主标题提示“准备今天这一顿”；
- 游客、草稿、档案不完整和数据失败状态同样使用意图型主标题，避免标题与按钮机械重复。

## 7. H2.4 返回页面的数据失效与按需刷新

2026-08-18 根据首页返回时内容先清空的问题，将首页和记录页统一为“版本失效、按需刷新”的策略：

- `services/dataInvalidationService.js` 维护 `meals` 与 `profile` 两个领域版本；本餐、狗狗档案、体重和护理写入成功后推进对应版本，登录切换推进全部版本。
- 首页记录最近一次读取的版本、上海自然日和认证状态；普通 Tab 往返直接复用已有快照，跨天、认证变化或数据版本变化才重新读取。
- 首页在已有快照上刷新时保留旧内容，使用“正在更新首页内容”提示；后台读取失败时保留旧内容并提供重新加载入口。
- 记录页继续复用统一时间轴的月份缓存；只有领域版本变化或明确重试/刷新时才强制读取，读取期间保留已有月份模型。
- 首页与记录页不共享展示模型，只共享失效信号；这样各页面可以保持自己的日期选择、事项汇总和错误降级语义。
