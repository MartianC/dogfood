# 剩余菜谱原料自动映射方案

## 1. 目标与边界

本文定义 `2026-08-11-v3` 标准食材目录之后，剩余菜谱原料写法的自动映射方案。目标是在没有人工逐条审核条件下继续提高身份覆盖率和营养可计算覆盖率，同时保持以下约束：

- 调味料和油不进入标准食材覆盖率分母。
- 烹饪辅料单独分流，不建立营养食材概念。
- 模型只提供受控身份候选，不能直接选择营养来源或发布数据。
- 一个标准食材概念只能有一个营养来源。
- 优先生鲜、未经烹调、去骨、去皮、无调味且可直接烹调的来源；没有理想来源时才按受控降级顺序选择其他形态。
- 不允许用相似但身份不同的食材营养值代替缺失来源。
- 新标准概念的犬食安全状态保持 `unknown`，安全策略不在原料映射阶段推断。

## 2. 真实缺口口径

模型合并报告中的1,559组隔离项不是全部仍未覆盖。部分写法后来通过其他高置信组建立的概念得到确定性映射，另一些本应归入调味料、油或烹饪辅料。

以 v3 完整目录重新执行确定性清洗后，真正的核心身份或来源缺口为1,418组、48,398次提及：

| 队列 | 组数 | 提及次数 | 处理方向 |
|---|---:|---:|---|
| 模型未决 | 765 | 20,979 | 使用受控候选重新分类 |
| 字面门禁失败 | 399 | 13,466 | 区分安全别名、状态映射和模型误判 |
| 无唯一营养来源 | 254 | 13,953 | 建立来源基础身份聚类或扩充营养底库 |
| 规则漏判的调味料 | 60 | 1,330 | 完善排除规则，不建立标准概念 |
| 油类规则漏判 | 4 | 39 | 修复完整词匹配和误伤 |
| 烹饪辅料 | 4 | 37 | 标记为 auxiliary，不建立营养概念 |

核心缺口高度集中：

- 前22组覆盖核心缺口提及量的25%。
- 前93组覆盖50%。
- 前100组共25,063次提及，占核心缺口的51.8%。
- 如果前100组全部可靠解决，当前严格口径覆盖率理论上可从45.89%提升至约62.68%。

因此不得按名称字典顺序处理，应先处理前100个高频组，再逐步下沉到长尾。

## 3. 决策结果分类

每个原料身份组最终必须落入以下一种结果：

| 结果 | 含义 | 是否进入标准概念 | 是否可计算营养 |
|---|---|---:|---:|
| `mapped_existing` | 映射至既有概念 | 否 | 是 |
| `new_concept` | 建立具有唯一来源的新概念 | 是 | 是 |
| `identity_only` | 身份明确但缺少可靠来源 | 候选态 | 否 |
| `conversion_required` | 身份明确，但菜谱状态与基准来源需要重量换算 | 否 | 暂否 |
| `composite` | 组合原料，可拆成多个已有概念 | 否 | 组件全部就绪后可计算 |
| `excluded` | 调味料或油 | 否 | 不参与覆盖统计 |
| `auxiliary` | 水、酵母、泡打粉等辅料 | 否 | 否 |
| `ambiguous` | 上位词、身份不足或候选冲突 | 否 | 否 |

身份覆盖率和营养可计算覆盖率必须分开统计。不能因为已经知道“它是什么”，就把缺少来源或缺少状态换算的项目视为营养可计算。

## 4. 阶段一：修复确定性规则

这一阶段不调用模型。

实施状态（2026-08-12）：当前规则为 `recipeIngredientNormalization/v3`。阶段二确认的新概念写入 `2026-08-12-v4` 完整目录后，从原始来源重建 SQLite 并重新执行阶段一；33,930个词项中14,620个得到确定性决定，19,310个保留未决。辅料、调味料和状态换算三个漏判队列均为0；12个状态词项、908次提及保留 `conversion_required`，33个状态词项、632次提及为 `ready`。严格分母为147,265次，身份覆盖81,653次、55.45%。最终产物位于 `fooddata-cloudbase-export/2026-08-12-stage1-deterministic-v4/`，未写入CloudBase。

### 4.1 调味料归一

繁体、异体、刀工和常见别名应先统一，再进入调味料排除：

- `麻椒 → 花椒`
- `醬油 → 酱油`
- `蔥花、蔥段 → 葱`
- `薑片、薑末 → 姜`
- `白沙糖、细沙糖 → 白糖`
- `味增 → 味噌`

这些结果标记为 `excluded_seasoning`，不建立标准食材概念。

### 4.2 油类规则

油类使用完整词或受控别名匹配，不允许普通子串匹配。当前需要专门防止：

- `牛油` 误伤 `牛油果`。
- `鳄梨 → 牛油果` 被错误归入油类。
- `粟米油 → 玉米油` 未命中油类排除。

### 4.3 烹饪辅料

- `冷开水、热水、纯净水 → 水`
- `即发酵母粉、即溶酵母 → 酵母`
- `老面 → 发酵辅料`

这些写法保留原料提及事实，但映射结果为 `auxiliary`。

### 4.4 高置信别名

只有不改变物种、部位和制品类型的关系才能自动批准，例如：

- `红枣 → 枣`
- `马苏里拉芝士 → 马苏里拉奶酪`
- `红萝卜 → 胡萝卜`
- `豆角 → 四季豆`
- `芝士 → 奶酪`
- `冬笋、春笋 → 竹笋`
- `圣女果 → 番茄`
- `马蹄 → 荸荠`
- `龙眼 → 桂圆`（目录别名；标准概念名保持“桂圆”）
- `玉米面 → 玉米粉`

## 5. 阶段二：建立来源基础身份聚类

当前“无唯一营养来源”并不都表示底库缺数据。牛奶、木耳、芝麻、玉米等在 Foundation 或 SR Legacy 中存在档案，但中文包含匹配不能稳定识别基础身份。

应从8,262条来源档案自动解析以下身份字段：

```text
基础身份：milk / sesame / corn / wood-ear-mushroom
物种：chicken / pork / beef / wheat
部位：breast / wing / rib / liver
加工形态：raw / cooked / dried / canned / cured
骨皮状态：boneless / skinless / bone-in
附加处理：salted / sweetened / fortified / flavored
```

来源处理流程：

```text
Foundation / SR Legacy 档案
  → 英文基础身份解析
  → 同一基础食材聚类
  → 排除调味、复合食品和身份冲突
  → 生鲜或未经烹调优先
  → 去骨、去皮、无调味优先
  → readyToCookNutritionSource/v1 选择唯一来源
```

聚类必须以英文身份为主，中文来源名只作为检索桥梁，不能再用“中文名包含基础名”直接确认身份。

优先处理以下高频来源缺口：

- 牛奶：3,423次。
- 木耳及黑木耳：1,100次。
- 芝麻及白/黑芝麻：1,542次。
- 玉米：400次。
- 紫薯：259次。
- 椰蓉：252次。
- 香肠：227次。
- 菠萝：223次。
- 冬瓜：219次。
- 椰浆：210次。

牛奶的全脂、低脂、脱脂和强化状态必须先聚成一个“牛奶”基础概念，再从候选档案中选择唯一基准来源，不能分别建立多个标准概念。

实施状态（2026-08-12）：阶段一的19,779个未决词项已经按 `recipeIngredientStage1Routing/v1` 保存为7个互斥队列，词项和提及次数均守恒。进入阶段二的23个来源精确项与15,026个身份候选由 `sourceFoodBaseIdentityClustering/v2` 处理；8,262条来源档案形成1,350个英文基础身份簇，其中8,261条具有营养明细，缺少营养明细的档案仍保留身份但不得被选择。

阶段二只允许受控中英身份约束自动通过。中文机器译名只能检索候选；仅凭中文桥接得到的“油菜→Chayote”“牛蒡→Bockwurst”等结果统一标记为 `bridge_only_unverified`，不能生成决定。首轮11个高置信身份簇覆盖9,738次提及，选择11个不重复来源：牛奶、芝麻、木耳、玉米淀粉、可可粉、柠檬、玉米、酸奶、菠萝、冬瓜和椰浆。玉米淀粉与玉米补入既有概念别名，其余9簇已写入本地 `2026-08-12-v4` 完整目录；目录现有200个概念、715个别名和200个唯一来源。用新目录重跑阶段一后，阶段二 v5 的高置信可接收簇为0，说明本轮决定已全部被目录吸收；仍未写入CloudBase。

## 6. 阶段三：受控候选模型

模型未决项不得再次使用开放式“生成基础名”提示。每个输入只允许从检索得到的候选和固定结果类型中选择：

```text
输入：奶油奶酪

候选：
1. ingredient_cream_cheese
2. ingredient_heavy_cream
3. ingredient_cheese
4. new_concept
5. composite
6. excluded
7. auxiliary
8. ambiguous
```

自动通过必须同时满足：

- 模型选择与确定性规则不冲突。
- 食材一级分类一致。
- 动植物物种和肉类部位一致。
- 制品类型一致。
- 候选概念具有唯一营养来源。
- 不是品牌菜品、复合加工食品或身份不足的上位词。
- 第一候选与第二候选达到规定的得分差距。

模型只能输出候选 ID 或受控状态，不能输出自由文本营养来源。

适合进入新概念候选的高频项目包括可可粉、柠檬、培根、酸奶、奶油奶酪、吉利丁、银耳、面条、腐竹、百合、紫菜、火龙果和蛤蜊。

以下项目原则上继续隔离或分流：

- `肉馅、肉丝`：缺少动物身份。
- `青红椒`：组合原料，应拆成两个组件。
- `火腿肠、肉松、老干妈`：加工或品牌复合食品。
- `高汤、鸡汤`：组成不稳定。
- `可乐`：不属于基础烹调食材。
- `开水、热水、纯净水`：烹饪辅料。

实施状态（2026-08-12）：阶段三已按 `recipeIngredientStage3CandidatePreparation/v1`、`recipeIngredientStage3DualPassModel/v1` 和 `recipeIngredientStage3CatalogIntegration/v1` 完成。阶段二 v5 的30个来源身份组、1,436次提及先经过身份门禁：13组、1,021次提及形成确定性唯一决定；4组、30次提及进入本地模型；13组、385次提及因上位词、复合加工食品、组成不明或缺少可食部位直接隔离。

本地模型只处理“小麦粉、大豆、李子、菊苣”4组，并分别以候选正序和倒序执行两次。两次均一致返回 `ambiguous`，因此模型选择来源数为0、分歧数为0、隔离数为4；本地共使用1,530 token，外部API token成本为0。模型没有自由生成来源ID，也没有直接写入目录。

13个确定性决定最终新增11个标准概念：培根、面条、绿豆、樱桃、长豆、榛子、覆盆子、黑莓、意大利细面、木薯和野鸡；“奶油”补入既有淡奶油概念别名，“鸭子”补入既有鸭肉概念别名。目录由200个概念扩展到211个概念、728个别名和211个唯一来源。生鲜水果未明确写 `unsweetened` 时仍按天然未加糖处理；明确含 `sweetened`、糖浆、加糖或 `all flavors` 的来源继续受加工惩罚。“意大利细面”额外要求英文来源命中 `spaghetti`，避免选择宽泛意面簇中的菠菜鲜意面。存在错误来源选择的阶段三初版 `2026-08-12-v5` 仅保留为历史产物，正式结果以 `2026-08-12-v6` 为准。

用 v6 目录重建 SQLite 并重跑阶段一后，决定为14,673项、284,264次提及，未决为19,257项、56,527次提及；辅料、调味料和状态换算漏判均为0。按只排除调味料和油的固定分母，覆盖率由阶段三前的81,653 / 147,265（55.45%）提升到82,862 / 147,265（56.27%），提升0.82个百分点。重新生成阶段二 v6 和阶段三 v3 后，确定性可接收组为0；只剩此前已双次一致隔离的4个模型组和13个预隔离组，说明本轮13个决定已全部被目录吸收。

当前结果仍是离线 staging：未写入 CloudBase、未切换线上活动版本。新增概念在未来生成运行时投影前，必须生成与 v6 目录完全匹配的犬食安全策略快照；没有自动规则证据的概念保持 `unknown`，不得因缺少人工审核而默认允许。

## 7. 阶段四：处理字面门禁失败

字面门禁不能整体放宽，必须分为三类。

### 7.1 安全别名

在概念、物种和部位均一致时直接映射，例如红萝卜、芝士、冬笋、圣女果、马蹄和桂圆。

### 7.2 身份一致但状态不同

以下项目可以映射到同一个标准概念，但原料提及层必须保留状态：

- `米饭 → 大米`
- `全蛋液、蛋液 → 鸡蛋`
- `熟芝麻 → 芝麻`

建议为原料提及或映射结果增加：

```text
mention_preparation_state = raw | cooked | dried | unknown
nutrition_status = ready | conversion_required | unavailable
```

例如100克熟米饭不能直接套用100克生大米的营养值。没有可靠熟重到生重换算时，身份可以映射，但营养状态必须为 `conversion_required`。

### 7.3 明确模型误判

以下提议必须丢弃并重新检索，不能加入别名字典：

- `牛腩 → 牛腭`
- `莴笋 → 莜麦`
- `鹌鹑蛋 → 鹧鸪蛋`
- `鲈鱼 → 鲳鱼`
- `薏米 → 薥米`
- `茭白 → 茡白`

这些反例必须固定为回归测试哨兵。

### 7.4 Wave A 实施结果

实施状态（2026-08-12）：阶段四首轮已按 `recipeIngredientStage4IdentityLexiconIntegration/v1` 完成。版本化身份词典 `2026-08-12-wave-a-v1` 完整覆盖阶段一 `identity_candidate` 中频次不少于100次的57项、9,525次提及；词典将每项互斥分配为既有概念别名、新概念或隔离项，遗漏、额外项和重复分配都会使整批失败。

本轮接受24项、3,761次提及，其中7项补入既有概念：普通面粉、高筋粉、鸡蛋清、猪里脊肉、肋排、娃娃菜和口蘑；17个写法收敛为15个新概念：奶油奶酪、吉利丁、苦瓜、莴笋、鹌鹑蛋、猪蹄、黄豆、核桃、红辣椒、黄豆芽、西米、荷兰豆、绿豆芽、紫菜和鸡爪。每个新概念必须同时命中受控英文描述正则、允许的 USDA 来源分类和至少一条营养明细，再按统一来源评分选择唯一基准。鸡爪没有生鲜来源，按“无生鲜时才允许其他形态”的降级规则选择唯一水煮来源；发布和营养计算时必须保留该来源状态，不能伪装成生重数据。

其余33项、5,764次提及继续隔离，主要原因包括：缺少精确来源（银耳、紫薯、抹茶粉、火龙果等）、物种或部位不足（里脊肉、豆芽、鲫鱼、草鱼）、加工组成不稳定（香肠、腊肉、腊肠、奶酪）、需要形态换算（椰蓉、虾皮、虾米、海苔）以及组合原料（青红椒）。这些项目没有为了提高覆盖率而套用相似食材来源。

正式本地目录为 `2026-08-12-v7`，由211个概念、728个别名和211个来源扩展为226个概念、754个别名和226个唯一来源。重建 SQLite 并重跑阶段一后，未决提及由56,527降至52,561；按只排除调味料和油的固定分母，覆盖率由82,862 / 147,265（56.27%）提升到86,828 / 147,265（58.96%），增加3,966次提及、提升2.69个百分点。新增标准名还吸收了相关规格和切法写法，因此实际提升高于词典直接接受的3,761次。

当前结果仍为离线 staging：未生成与 v7 完全匹配的犬食安全策略快照，未写入 CloudBase，也未切换线上活动版本。

### 7.5 Wave B 实施结果

## 9. 低频长尾身份组映射方案

### 9.1 范围与原则

首轮低 token 队列只处理聚合频次至少5次的1,851组。其余13,824个身份组共17,947次提及，聚合频次均低于5次，继续延后。低频长尾不等于无价值，但它包含更多错别字、品牌、用途说明、复合菜名和只出现一次的噪声，不能直接沿用高频组的开放式模型处理方式。

长尾处理遵循以下原则：

- 先用最新目录和规则重新归一，已经被 v4 或后续目录覆盖的写法直接移出队列。
- 处理单位仍是清洗后的身份组，不把同一身份的原始写法分别发送给模型。
- 频次1的项目原则上不调用模型，除非能够检索到唯一既有概念或唯一来源身份簇。
- 不因长尾数量大而降低身份、来源或发布门禁。
- 主要优化目标是提及覆盖率和营养可计算覆盖率，不追求把每个只出现一次的噪声词都变成标准概念。

### 9.2 每轮先重新基线化

每次处理长尾前必须使用最新完整目录重新执行：

```text
原始长尾身份组
  → 最新调味料/油规则
  → 最新辅料规则
  → 最新概念与别名
  → 最新来源基础身份簇
  → 剩余真实长尾队列
```

重新基线化后输出以下数字：

- 原始13,824组中已由新别名覆盖的数量。
- 新识别出的调味料、油和辅料数量。
- 仍需候选检索的身份组数和提及次数。
- 频次4、3、2、1各层的组数和提及次数。

禁止复用旧报告中的长尾数量直接生成下一轮模型队列。

### 9.3 四层处理队列

| 层级 | 条件 | 处理方式 | 是否调用模型 |
|---|---|---|---:|
| L0 确定性层 | 命中排除、辅料、既有别名、繁简转换、受控错别字或状态/刀工规则 | 直接生成决定 | 否 |
| L1 唯一候选层 | 只检索到一个概念或一个来源身份簇，且类别、物种、部位一致 | 机器门禁后自动映射 | 否 |
| L2 受控模型层 | 有2至5个可信候选，无法靠规则唯一决定 | 模型只能选候选或返回受控隔离状态 | 是，本地模型 |
| L3 隔离层 | 无候选、候选冲突、上位词、复合食品、品牌噪声或来源缺失 | 保留原因并延后 | 否 |

L0和L1必须先跑完并更新候选索引，L2不能与它们并行使用旧目录。L3不重复消耗模型计算，只有目录、来源底库或规则版本变化后才重新入队。

### 9.4 频次优先级

长尾按聚合频次从高到低分波次处理：

1. 频次4。
2. 频次3。
3. 频次2。
4. 频次1中命中L0或L1的项目。
5. 频次1中仍需模型判断的项目最后处理，默认保持延后。

同频次内按以下顺序排序：

1. 能映射到既有概念的候选。
2. 有唯一来源身份簇的新概念候选。
3. 能补齐多个原始别名的身份组。
4. 身份明确但需要状态换算的项目。
5. 来源缺失、复合或歧义项目。

### 9.5 模型节省策略

长尾模型调用只允许使用本地模型，并执行以下压缩：

- 输入只包含 `cleaned_name`、最多3个代表性原词、频次和2至5个候选 ID。
- 不发送完整菜谱、营养明细或已经确定的调味料/油项目。
- 相同清洗身份、候选集合和规则版本使用结果缓存。
- 模型输出固定为 `candidate_id / new_concept / composite / excluded / auxiliary / ambiguous`。
- 每个分片建议50组，即时落盘并支持断点续跑。
- 频次1且没有候选的项目不调用模型，直接进入L3。

本地模型不产生外部 API token 成本，但仍记录输入和输出 token 估算、运行时间、模型版本和缓存命中率，用于判断继续处理的边际收益。

### 9.6 自动通过门禁

长尾结果只有满足以下条件才能自动通过：

- 候选是既有概念，或新概念具有唯一来源身份簇。
- 食材类别、物种、部位和制品类型全部一致。
- 不触发模型误判哨兵或跨概念别名冲突。
- 模型没有把上位词缩窄成未经输入支持的具体物种或部位。
- 状态不同但身份相同的项目保留 `mention_preparation_state`。
- 需要重量换算但缺少换算依据时标记 `conversion_required`。
- 新概念通过 `readyToCookNutritionSource/v1` 选择唯一来源。
- 无来源时只生成 `identity_only/source_missing`，不生成营养代理值。

单次出现的词只有在L0确定性命中，或L1同时具有唯一概念、唯一来源身份和零冲突时才能自动进入正式映射。

### 9.7 分波次发布

长尾不得一次性生成一个不可审计的大版本。建议每个目录版本最多接收：

- 2,000个待判定身份组；或
- 200个新增标准概念；或
- 以前一条件先达到者为准。

每个波次按以下流程执行：

```text
冻结输入和规则版本
  → L0/L1确定性处理
  → L2本地模型处理
  → 合并器与来源选择器
  → 重建新SQLite
  → 完整性和覆盖率验证
  → 生成隔离报告
  → 进入下一波次
```

任何波次失败时只废弃该波次候选，不修改上一版完整目录。

### 9.8 停止条件

满足任一条件时停止继续向更低频层调用模型：

- 本波次营养可计算覆盖率提升小于0.1个百分点。
- 新增候选中超过80%因身份不足或来源缺失被隔离。
- 频次1项目没有唯一候选。
- 新增概念无法满足一概念一来源。
- 候选错误哨兵、别名冲突或来源重复不为0。

停止不表示删除长尾。未解决项继续保留在版本化隔离报告中，等待新目录、来源底库或规则版本触发重算。

### 9.9 长尾验收指标

每个长尾波次至少报告：

- 输入身份组数、提及次数和频次分布。
- L0、L1、L2、L3各层数量。
- 模型实际处理组数、缓存命中数和外部 API token 成本。
- 映射至既有概念、新增概念、状态换算、来源缺失和歧义数量。
- 身份覆盖率变化。
- 营养可计算覆盖率变化。
- 调味料和油排除数量。
- 重复来源、跨概念别名冲突、外键错误和完整性检查结果。

## 10. 自动化产物

候选报告必须保留原词、清洗词、基础身份、候选来源、机器规则版本、模型版本和最终拒绝原因，保证全流程可重放。

## 12. 发布门禁

任何新目录只有同时满足以下条件才能进入 staging：

- 每个标准概念恰好一个营养来源。
- 重复来源为0。
- 跨概念别名冲突为0。
- 外键错误为0，`integrity_check=ok`。
- 来源英文身份与标准概念一致。
- 状态换算缺失时不输出营养计算结果。
- 模型输出不能直接发布。
- 无可靠来源时不使用近似营养值。
- 新概念的犬食安全策略自动补为 `unknown`。
- 调味料和油继续从覆盖率分母排除。

本方案只定义离线自动化和 staging 前门禁，不授权写入 CloudBase、切换活动目录版本或发布生产数据。
