# “和狗狗一起吃”记录打卡方向转型实施计划

**状态：** 产品方向已确认，等待按阶段执行

**日期：** 2026-07-26

**目标：** 将小程序从“浏览狗饭食谱并生成批量制作清单”转为“选择这一顿的人饭菜单，生成可调整的狗饭初稿，完成本餐评估并保存打卡记录”。

## 1. 已确认的产品决策

本计划以下列决定为固定前提，执行过程中不得重新解释为旧产品流程：

1. “一起吃”表示从人饭菜谱中提取可共用的基础食材，为狗狗单独制作无调味狗饭，不表示把做完的人饭直接分给狗狗。
2. 一次打卡只对应一只狗狗：
   - 只有一只狗狗时自动选中。
   - 多只狗狗时，进入菜单搜索前选择本次对象。
   - 同一人饭菜单可以分别为多只狗狗生成独立打卡，但不共用一份克重。
3. 所有未被安全策略阻断的目录食材都可以被搜索、添加和自动带入狗饭初稿。
4. 用户界面只表达“可加入”和“被阻止”：
   - 不向用户展示 `allowed / conditional / unknown / blocked` 四态。
   - 被阻止时展示当前安全策略提供的原因。
5. 初始总量由目标狗狗的本餐能量需求决定。
6. 食材比例根据当前适用营养标准进行确定性优化，不使用人饭菜谱原始分量。
7. 食材过少、品类单一或无法满足全部营养目标时仍允许生成，不自动补齐食材；不足之处由本餐评估展示。
8. 用户可在狗饭预览中调整克重，也可额外搜索添加人饭菜单中不存在的食材。
9. 保存结果就是一次计划中的本餐打卡，不区分“计划吃”和“已经吃”。
10. 当前本餐评估的能量与营养密度双轴结构继续保留。

## 2. 产品边界

### 2.1 一句话定位

> 选好自己这一顿吃什么，用其中可共用的食材为狗狗生成一份专属狗饭，并记录这次一起吃饭。

### 2.2 产品承诺

系统生成的是“可调整的狗饭初稿”，不是保证营养完整、适合长期连续喂养的处方。

界面需要持续说明：

- 狗饭必须与人饭分开制作，不继承人饭中的盐、油、酱汁和调味方式。
- 初始克重是根据狗狗档案、食材营养数据和所选标准计算的参考值。
- 食材组合不足时仍可保存，本餐评估会如实展示不足或数据缺失。
- 有特殊健康问题时应咨询兽医或宠物营养专业人士。

### 2.3 本轮不做

- 不做多只狗狗共用一份克重的狗饭。
- 不做计划与已食用两套状态。
- 不从人饭原始分量推导狗饭克重。
- 不自动加入人饭菜单之外的补充食材或营养补充剂。
- 不因营养不足阻止保存。
- 不把一次打卡自动保存为长期食谱；后续可增加“保存为常用搭配”。
- 不删除旧批量制作代码和数据；迁移期先隐藏旧入口，确认新流程稳定后再单独清理。

## 3. 目录事实与食材操作规则

### 3.1 `ingredient_catalog` 字段边界

`ingredient_catalog` 只保存目录事实和当前有效安全策略状态，不保存搜索、添加或编辑等产品操作资格。

保留：

- 目录、策略和营养来源版本。
- `concept_id`、`variant_id`、`food_id`。
- 中文名称、别名、分类和食材形态。
- `policy_status`。
- `is_default`；它表示一个食材概念的默认营养形态，属于目录结构事实，不是产品权限。

移除：

- `is_searchable`。
- `is_selectable`。
- `is_editable` 及其他表示产品操作资格的布尔字段。

`canine_ingredient_policies` 继续保存完整策略、条件、证据、理由和审核信息。生成目录投影时按“形态策略优先、概念策略回退、缺失为 unknown”解析出唯一 `policy_status`；不得在 CloudBase 控制台手工维护目录中的策略结果。

### 3.2 统一食材操作规则

搜索、添加和自动带入由一个纯规则模块集中判断：

```javascript
function canSearchIngredient(ingredient) {
  return ingredient.policyStatus !== 'blocked'
}

function canAddIngredient(ingredient) {
  return ingredient.policyStatus !== 'blocked'
}

function canAutoIncludeIngredient(ingredient) {
  return ingredient.policyStatus !== 'blocked'
}
```

三个函数当前采用同一规则，但必须保留各自明确的业务命名，方便未来独立调整。页面、服务和云函数不得散落编写自己的 `policyStatus !== 'blocked'`。

具体要求：

- `allowed / conditional / unknown` 均可搜索、添加和自动带入。
- `blocked` 不可添加或自动带入。
- blocked 的具体原因由云函数根据 `concept_id / variant_id / policy_version` 读取 `canine_ingredient_policies` 后返回经过整理的用户文案。
- 客户端负责交互过滤，保存狗饭的云函数必须使用同一规则再次校验，防止旧客户端或伪造请求绕过。
- 人饭原料未成功映射到目录项时，页面保留原始文字，不提供直接加入操作；用户仍可通过“添加食材”搜索已发布目录。
- 营养数据能否用于计算或排行由营养服务检查实际数据，不写回 `ingredient_catalog` 的权限型布尔字段。

### 3.3 当前不一致

截至 2026-07-26，仓库存在两种口径：

- CloudBase 投影中的 `is_selectable=true` 仍只覆盖明确 `allowed` 或可执行条件项。
- 普通食材搜索已在 2026-07-24 改为 `policy_status != blocked`，允许 `allowed / conditional / unknown` 搜索和添加。
- 人饭菜谱 `has_selectable_ingredients` 和营养素排行仍依赖旧的严格 `is_selectable`。

当前搜索还同时查询 `is_searchable=true`，但导出器对全部已发布目录项都写入 `true`。这些字段已经失去清晰语义，且让人饭自动带入、手动添加和营养排行产生不同结果。

### 3.4 数据迁移要求

- 从 `ingredient_catalog` 投影和 Schema 契约中移除 `is_searchable`、`is_selectable` 等权限型字段。
- 新增统一食材操作规则模块，并让目录搜索、人饭自动带入、额外添加和云端保存复用。
- 重新生成 `ingredient_catalog`、`human_recipes` 和依赖旧 `is_selectable` 的派生集合。
- 人饭菜谱组件只内嵌 `policy_status`；能否加入由统一食材操作规则判断。
- 营养素排行根据统一食材操作规则筛选安全候选，再根据实际营养记录判断是否能够参加目标营养素排行。
- 更新安全策略、菜谱映射和营养排行 SOP，删除对旧 `is_selectable` 的依赖。
- blocked 详情由受控云函数读取策略集合并生成用户文案，客户端不能直接读取完整审核记录。
- 发布新版本到 staging，完成数量、样本、阻断原因和回滚验证后再切换活动版本。

### 4.3 数据结论

- 当前数据足够支持开发和测试，不需要在开始页面开发前继续扩大目录。
- 旧 searchable 投影只有 6,082 道菜，是旧严格 `is_selectable` 口径的结果，不能作为新产品覆盖基线。

- 多数候选菜只能自动带入 1 个食材。这不阻塞本轮，因为已确认食材过少仍允许生成，用户可额外添加，营养不足由本餐评估展示。
- 映射覆盖仍较低，但它是上线内容质量问题，不是开发阻塞项。首轮测试应优先使用具有肉类、主食和蔬菜映射的稳定样本。

## 5. 信息架构与主流程

### 5.1 底部导航

新主流程采用 3 个 Tab：

1. 首页
2. 记录
3. 我的

旧“食谱”和“清单”不再作为主 Tab。迁移期保留原页面代码和路由，但不在新信息架构中暴露入口。

### 5.2 主流程

```text
首页大加号
  → 登录/建档守卫
  → 选择本次狗狗（单狗自动跳过）
  → 搜索并选择多道人饭
  → “这顿就吃这些吧”
  → 生成狗饭初稿
  → 增删可共用食材
  → 调整狗饭克重
  → 可选：额外添加食材
  → 查看本餐评估
  → 保存并打卡
  → 本餐记录详情
```

中途退出时保留本地草稿。重新进入大加号时，如果存在未完成草稿，提供“继续编辑”和“重新开始”。

## 6. 页面设计要求

### 6.1 首页

页面目标：快速发起一顿记录并回看最近记录。

核心内容：

- 今日日期和生活化问候。
- 狗狗摘要；多狗家庭只显示档案列表或最近记录，不建立全局默认狗。
- 主操作大加号：“记录一起吃的一顿”。
- 最近一次打卡摘要。
- 最近记录列表入口。

点击大加号后才执行登录和建档守卫，启动时不强制授权。

### 6.2 本次狗狗选择

- 只有一只有效档案时自动选择并继续。
- 多只狗狗时展示单选列表。
- 不提供多选。
- 档案缺少本餐能量计算必需字段时，进入档案完善页；完成后返回当前草稿，不回首页。

### 6.3 人饭菜单搜索

页面结构：

- 顶部搜索框。
- 默认态可展示最近搜索、常见菜或推荐菜。
- 搜索结果列表。
- 已选菜单摘要。
- 固定底部确认栏。

菜谱结果卡：

- 标题、分类和可带入狗饭的食材数量。
- 点击卡片主体只展开或收起原料列表。
- 选择控件独立于展开操作。
- 展开后按来源顺序展示全部人饭原料。
- 能映射且 `canAutoIncludeIngredient()` 返回 `true` 的原料显示“可用于狗饭”。
- `policy_status=blocked` 的原料显示阻断原因。
- 未映射原料只显示来源文字，不制造安全判断或目录身份。

底部确认文案：

```text
已选 3 道菜
[这顿就吃这些吧]
```

至少选择一道菜后才能继续。菜谱即使只有一个可加入食材，也允许选择。

### 6.4 狗饭创建页

页面固定为四个区域。

#### A. 今天的人饭

- 按每道菜分组。
- 展示全部来源原料。
- 可加入原料默认加入狗饭初稿。
- 用户可以将可加入原料从狗饭中移除或重新加入。
- 这里不编辑狗饭克重。
- 操作文案使用“加入狗饭 / 从狗饭中移除”，不使用会修改来源事实的“删除原料”。
- blocked 项保持禁用并显示原因。

#### B. 狗狗这顿吃什么

- 按标准食材概念合并重复项。
- 每个食材展示名称、克重、称量口径和来源。
- 来源可能是多道人饭，也可能是“额外添加”。
- 用户在这里调整克重或从狗饭中删除食材。
- 修改后实时重算总重、能量与本餐评估。
- 克重使用整数克展示；内部计算可以保留更高精度。

#### C. 额外添加食材

- 复用并改造现有独立食材搜索页。
- 只返回 `canSearchIngredient()` 为 `true` 的目录项。
- 选择后输入克重并加入当前草稿。
- 重复食材合并，不生成重复行。
- 额外添加食材不伪造成人饭来源。

#### D. 本餐评估

- 继续展示“份量与能量”和“营养密度”两个独立结论。
- 初稿生成后立即评估。
- 任一食材增删或克重变化后重新评估。
- 营养不足、品类单一或部分数据缺失不阻止保存。
- 页面底部固定主操作“保存并打卡”。

### 6.5 记录列表

- 按日期倒序展示。
- 每条记录展示狗狗、用餐时间、人饭菜名摘要、狗饭食材数和评估摘要。
- 支持日期分组和空状态。
- MVP 不做社交分享、连续打卡奖励或复杂统计。

### 6.6 记录详情

- 狗狗档案快照。
- 人饭菜单快照及各菜原料。
- 最终狗饭食材和克重。
- 本餐评估快照。
- 计算所使用的数据、目录、策略、标准和算法版本。
- 可选照片和备注。
- 详情默认只读；后续如需修改，使用“复制为新的一顿”，不直接改变历史记录。

## 7. 初始克重与比例分配

### 7.1 口径说明

营养标准提供的是能量和营养素目标或范围，不直接提供“鸡肉占多少、胡萝卜占多少”的固定食材比例。

因此“比例按照营养标准确定”在实现中解释为：

> 在保持本餐能量接近目标的前提下，寻找使当前适用营养标准偏差尽量小的一组食材克重。

算法只生成确定性的参考初稿，不保证所有营养指标都能满足。

### 7.2 输入

- 目标狗狗档案。
- 每日餐数。
- 当前适用的生命周期、活动水平和标准档案。
- 用户当前选择且 `canAddIngredient()` 为 `true` 的食材。
- 每个食材的营养来源形态和每 100g 营养数据。
- 当前标准版本和算法版本。

### 7.3 计算步骤

1. 使用现有 `energyRequirementService` 计算每日能量目标。
2. 按每日餐数得到本餐能量目标。
3. 将当前选择食材按 `conceptId` 去重，保留明确 `variantId` 和 `foodId`。
4. 使用适用的国标与 FEDIAF 档案生成统一、可比较的营养约束。
5. 为每种食材建立非负克重变量。
6. 以“接近本餐能量目标”为最高优先级。
7. 在能量约束下，最小化营养素偏低、偏高和比例不符合要求的归一化偏差。
8. 将结果四舍五入为整数克，再执行一次能量缩放和评估。
9. 输出克重、总量、总能量、评估结果和算法元数据。

算法必须满足：

- 同样的输入和版本得到同样的输出。
- 所有被选食材默认得到大于 0 的克重，除非营养数据不可计算。
- 只有一种食材时仍按能量目标生成其克重。
- 无法满足标准时返回当前最优结果，不失败、不自动添加食材。
- 不从人饭来源分量初始化权重。
- 不使用随机数、网络 AI 或不可追溯的自由生成结果。

### 7.4 国标与 FEDIAF

两个标准继续独立评估。初始分配服务不得把其中一个标准的结果伪装成全部标准的统一结论。

实施前需要把优化目标写成版本化配置，至少包含：

- 参与优化的营养素。
- 每个标准的权重。
- 最低值、最高值、比例项和无法比较项的处理方式。
- 标准间要求冲突时的确定性优先级。
- 允许的能量误差。
- 克重舍入规则和迭代上限。

默认策略建议为：

- 能量目标优先于营养密度优化。
- 国标与 FEDIAF 使用相同标准级权重。
- 同一营养素有多个最低要求时以较严格值参与初始分配。
- 发生无法同时满足的上下限冲突时保留两套独立评估，不将冲突作为生成失败。

该配置必须有固定测试夹具和 `allocationAlgorithmVersion`，调整权重视为算法版本变化。

### 7.5 缺失数据

- 缺少狗狗档案必需字段：不生成初稿，引导完善档案并保留菜单草稿。
- 食材缺少能量数据：该食材保留在草稿中，但不为其生成伪精确克重；页面要求用户手动填写并显示评估可能不完整。
- 食材缺少部分普通营养数据：仍可生成能量初稿，本餐评估按现有缺失数据规则降级。
- 标准数据加载失败：保留草稿和用户操作，允许重试，不静默使用硬编码默认标准。

### 7.6 克重基准

- 每个狗饭食材必须保留具体营养形态。
- 克重按该营养形态的数据基准计算，并在预览中以“生重、熟重、干重”等生活化文字说明。
- 不允许只展示抽象食材名却隐藏称量口径。
- 如果后续支持生熟转换，必须使用独立、可追溯的转换数据，不能按固定比例猜测。

## 8. 数据模型

### 8.1 本地草稿

```ts
type SharedMealDraft = {
  id: string
  targetDogId: string
  targetDogSnapshot: DogSnapshot
  mealTime: string
  selectedHumanRecipes: HumanRecipeSnapshot[]
  sourceIngredientSelections: SourceIngredientSelection[]
  dogMealItems: DogMealItem[]
  assessment?: MealAssessmentSnapshot
  catalogVersion: string
  policyVersion: string
  recipeVersion: string
  mappingVersion: string
  allocationAlgorithmVersion: string
  updatedAt: string
}
```

草稿默认保存在本地；保存并打卡成功后删除对应本地草稿。

### 8.2 人饭菜谱快照

```ts
type HumanRecipeSnapshot = {
  recipeId: string
  title: string
  categories: string[]
  sourceVersion: string
  recipeVersion: string
  ingredients: HumanIngredientSnapshot[]
}

type HumanIngredientSnapshot = {
  position: number
  rawName: string
  amountRaw?: string
  conceptId?: string
  variantId?: string
  foodId?: string
  displayName?: string
  policyStatus?: 'allowed' | 'conditional' | 'unknown' | 'blocked'
  blockedReason?: string
}
```

来源分量只保存为人饭快照，不进入狗饭克重计算。

### 8.3 来源食材选择

```ts
type SourceIngredientSelection = {
  humanRecipeId: string
  ingredientPosition: number
  conceptId?: string
  variantId?: string
  isIncludedInDogMeal: boolean
  decision: 'included' | 'removed' | 'blocked' | 'unmapped'
  reason?: string
}
```

`decision` 是记录和调试字段；用户界面不展示四态标签。

### 8.4 狗饭食材

```ts
type DogMealItem = {
  conceptId: string
  variantId: string
  foodId: string
  name: string
  category: string
  amountGram: number | null
  amountBasis: 'raw' | 'cooked' | 'dry' | 'other'
  originType: 'humanRecipe' | 'manual'
  originRefs: Array<{
    humanRecipeId: string
    ingredientPosition: number
  }>
  catalogVersion: string
  policyVersion: string
  nutritionSourceVersion: string
}
```

同一 `conceptId + variantId` 只保存一项；多个来源通过 `originRefs` 追踪。

### 8.5 本餐打卡记录

```ts
type SharedMealRecord = {
  id: string
  userId: string
  mealTime: string
  targetDogId: string
  targetDogSnapshot: DogSnapshot
  humanMenu: HumanRecipeSnapshot[]
  sourceIngredientSelections: SourceIngredientSelection[]
  dogMealItems: DogMealItem[]
  assessmentSnapshot: MealAssessmentSnapshot
  note?: string
  photoFileIds?: string[]
  versions: {
    recipeVersion: string
    mappingVersion: string
    catalogVersion: string
    policyVersion: string
    nutritionStandardVersion: string
    allocationAlgorithmVersion: string
  }
  createdAt: string
  updatedAt: string
}
```

历史记录保存快照，不依赖未来目录和算法版本重新解释。

### 9.1 页面建议

```text
pages/

  profile/index/index

subpackages/shared-meal/
  dog-select/index
```

页面名称可在实现前根据包体检查调整，但人饭搜索和生成流程应进入独立分包，主包只保留 Tab 页面和轻量摘要。

### 9.2 云函数建议

```text
cloudfunctions/
  searchHumanRecipes/
  getHumanRecipe/
  saveSharedMealRecord/
  listSharedMealRecords/
  getSharedMealRecord/
```

要求：

- 人饭菜谱只能通过云函数按活动 `recipe_version` 查询。
- 搜索接口支持关键词、分页和稳定排序。
- 列表返回紧凑摘要；展开时所需原料可随列表返回或按详情加载，但不能产生逐行云查询。
- 保存接口校验用户身份、狗狗归属、版本字段和食材结构。
- 云端不接受客户端自由覆盖公共菜谱、安全策略或营养数据。

### 9.3 可复用现有模块

- `energyRequirementService`：本餐能量目标。
- `nutritionDataService`：食材营养数据。
- `nutritionAssessmentService`：营养密度评估。
- `mealEnergyService`：本餐能量供给。
- `mealAssessmentService`：双轴结果。
- 独立食材搜索页面及列表组件。
- 狗狗档案、登录守卫和档案完善返回链路。
- UI Kernel 中的按钮、卡片、字段、标签、提示和空状态。

## 13. 完成定义

满足以下条件后，方向转型才算完成：

- 用户可从首页大加号选择一只狗狗和多道人饭。
- 搜索结果可展开查看全部人饭原料，展开与选择互不冲突。
- 所有非 blocked 食材可自动加入或手动搜索添加。
- 所有 blocked 食材不可加入且能说明原因。
- 系统按狗狗本餐能量目标和营养标准生成确定性初稿。
- 食材不足仍可继续，营养问题由本餐评估准确展示。
- 用户只在狗饭预览区编辑克重。
- 用户可额外添加食材并实时更新评估。
- 保存后生成包含完整快照和版本信息的本餐打卡记录。
- 新首页、记录列表、记录详情和我的页形成完整主路径。
- 数据、算法、页面、云函数、草稿恢复和真机核心路径均通过验证。
