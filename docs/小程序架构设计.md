# 狗饭小程序技术架构设计

更新时间：2026-08-02

## 1. 文档定位

本文描述当前“和狗狗一起吃”主线的运行架构、模块边界、依赖方向和可靠性约束。产品行为以
[`每日“和狗狗一起吃”单餐创建与记录 PRD`](./superpowers/specs/2026-07-26-shared-meal-checkin-prd.md) 为准；领域术语见
[`领域词汇表`](./domain/CONTEXT.md)，集合和索引见
[`数据库结构总览`](./database-structure-overview.md)。

旧公共狗饭食谱、制作周期和批量清单只作为兼容模块保留，不再定义当前主架构。

## 2. 架构目标与约束

- 使用微信小程序原生框架和 CloudBase，保持部署与运行边界简单。
- 页面只编排状态和导航，不直接访问云数据库，也不复制领域规则。
- 当前主流程以单狗、单餐、不可变记录为聚合边界。
- 食材操作资格统一由具名规则模块决定，页面、草稿服务和云函数不得散落比较 `blocked`。
- 系统只计算本餐能量目标；首次克重和食材比例由用户决定，不建设自动分配服务。
- 共享本餐不使用云存储，不提供照片选择、上传或展示；记录契约只兼容空 `photoFileIds`。
- 历史记录保存快照和版本，不能用当前档案、目录、标准或算法重算覆盖。
- 跨分包共享源码必须生成到各自分包，不能为了复用把运行时代码抬回主包。

## 3. 系统上下文

```text
用户
  │
  ▼
微信小程序页面
  │ 页面调用稳定服务接口
  ├─ 主包服务：鉴权、档案、记录、导航迁移
  └─ shared-meal 分包服务：人饭查询、草稿、评估、食材规则
  │
  ▼
  CloudBase adapter
  │
  ├─ login / dogProfile
  ├─ searchHumanRecipes / getHumanRecipe
  ├─ sharedMealRecord
  └─ weightRecord
  │
  ▼
CloudBase 集合
  ├─ users / dogs / shared_meal_records
  └─ 人饭、目录、安全策略、营养与标准的只读运行时投影
  ├─ weight_measurements
```

本地开发和自动化测试可通过 Mock adapter 提供相同业务接口；页面不感知当前使用 CloudBase 还是 Mock。

## 4. 运行时包结构

### 4.1 主包

主包保留四个当前 Tab 页面和全局服务：

```text
pages/home/index             首页与本餐入口、最近一顿
pages/records/index          月历、选中日记录列表
pages/dogs/index             狗狗档案中心
pages/profile/index/index    登录与账号信息

services/authService.js
services/dogService.js
services/homeStateModel.js
services/homeDraftSummaryService.js
services/sharedMealEntryService.js
services/sharedMealRecordService.js
services/sharedMealRecordMonthState.js
services/sharedMealRecordCalendarModel.js
services/navigationMigrationService.js
services/adapters/cloudbase.js | mock.js
```

subpackages/dog-profile/services/weightService.js

`app.json` 的底部导航固定为“首页、记录、狗狗、我的”，中央“记一顿”由自定义 TabBar 提供但不是 Tab。`pages/recipes/*` 和 `pages/plan/index/index` 仍注册在主包中，只用于旧深链兼容，不能重新进入 TabBar、中央动作或当前首页主路径。

### 4.2 `subpackages/shared-meal`

共享本餐主流程放在独立分包：

```text
dog-select/                  单狗自动选择、多狗单选、适用门禁、草稿恢复决策
menu-search/                 canonical 多菜搜索、分页、展开、多选和会话恢复
dog-select/menu-search/      保留 draftId 的旧嵌套路由兼容跳转壳
compose/                     来源操作、克重、双轴评估、保存
record-detail/               不可变快照详情与纯 view model
services/                    草稿、人饭查询、评估、食材规则和搜索会话
```

选狗、菜单和 compose 都消费同一个 `sharedMealDraft/v1`，避免用页面参数传递完整业务对象。

### 4.3 其他分包与兼容模块

- `subpackages/dog-profile`：档案新增、编辑和快速完善，仍服务当前建档往返。
- `subpackages/custom-recipe`：旧自定义狗饭与现有富含营养素食材入口；共享本餐只复用后者的既有能力和生成的评估服务，不把自定义狗饭变成当前人饭入口。
- `subpackages/plan-extra`：旧制作周期和历史批量清单详情，仅兼容保留。

### 4.4 跨分包唯一源码

`shared-src/subpackage-services` 保存以下跨分包服务的唯一源码：

- `meal-assessment/*`：能量需求、本餐能量、营养数据、营养密度和组合评估。
- `shared-meal/ingredientOperationRules.js`：非 `blocked` 操作资格。
- `shared-meal/sharedMealContract.js`：canonical 食材和稳定指纹。
- `shared-meal/sharedMealDraftService.js`：草稿、恢复、来源转换、评估快照和保存意图。

`scripts/sync-subpackage-services.js` 将源码生成到 `custom-recipe` 与 `shared-meal` 分包；`shared-src` 由 `project.config.json` 排除，不进入代码包。生成文件只能通过同步脚本更新。

## 5. 分层与依赖方向

```text
页面与组件
  → 页面 view model / 状态模型
  → 业务服务
  → adapter
  → 云函数
  → 集合或公共投影
```

### 5.1 页面层

- 负责生命周期、事件、局部加载/错误态和导航。
- 只消费稳定业务字段，不依赖 `_id`、`_openid` 或 TDesign 内部事件细节。
- 第三方 UI 只通过 `components/vendor/*` 或 `components/ui/*` 包装。

### 5.2 服务层

- 根 `services/` 提供跨主包页面使用的鉴权、档案、记录与月份状态。
- 分包 `services/` 提供只在目标分包运行的草稿、菜单会话、人饭视图和评估能力。
- 纯状态模型与 view model 不执行导航、不写云端，便于单元测试。
- `subpackages/dog-profile/services/weightService.js` 封装体重写模型；其 adapter 不直读集合。
- 体重 adapter 是对应云函数调用的唯一入口；原始体重云错误只在体重 service 中分类为稳定错误码，页面不依赖 CloudBase 错误文案。

### 5.3 云函数层

- 从 `wx-server-sdk` 上下文取得 OPENID，不信任客户端传入的用户标识。
- 校验输入、归属、活动版本和食材规则后访问集合。
- 只返回页面需要的业务 DTO，不把数据库权限判断下放到客户端。

## 6. 当前核心链路

### 6.1 登录与档案

```text
app.onLaunch
  → authService.initAuth
  → CloudBase/Mock adapter
  → login + dogProfile
  → globalData.authReady / authState / dogs
```

页面在读取个性化数据前等待 `authReady`。狗狗档案使用 `dogProfile/v3`，出生日期和日均活动时长是可信输入，生命阶段和活动档位由服务派生；特殊营养需求必须由用户显式确认。

### 6.2 创建与恢复本餐

```text
首页、记录空态或中央“记一顿”
  → sharedMealEntryService.startSharedMeal
  → dog-select 读取档案并计算 eligible/incomplete/blocked
  → sharedMealDraftService.getDraftRecoveryDecision
      ├─ none：继续当前选狗流程
      ├─ resumable：用户选择继续编辑或重新开始
      └─ invalid：只允许重新开始
  → canonical menu-search
  → searchHumanRecipes / getHumanRecipe
  → sharedMealDraftService 建立多菜来源草稿
  → compose 修改来源与克重并调用 meal-assessment
```

草稿写入 `wx.storage` 的 `sharedMealDraft/v1`。菜单页把关键词、分页结果、展开项和跨搜索选择序列化到草稿的 `menuSearchState`；返回页面时恢复，只有显式 reset 才随匹配草稿清除。

恢复可信草稿时会重新读取已选人饭详情，并用稳定菜单 ID、来源位置、目录身份和版本复核本地内容，不能把本地缓存直接当作可信云数据。

### 6.3 评估与保存

```text
当前草稿食材与克重
  → mealAssessmentService
      ├─ energyRequirementService / mealEnergyService
      └─ nutritionDataService / nutritionAssessmentService
  → 双轴评估快照
  → sharedMealDraftService.buildSaveIntent
  → sharedMealRecordService.save
  → CloudBase adapter
  → sharedMealRecord(save)
  → shared_meal_records
```

保存意图包含 `idempotencyKey`、`requestFingerprint`、canonical 食材、评估和版本快照。普通营养缺口不阻断保存；最高优先级偏高或关键数据缺失每个保存意图只确认一次。云函数重新校验狗狗归属、结构、活动版本和 `blocked` 食材，不能依赖客户端已经检查。

首次克重始终由用户填写。等比例调整只在用户已有完整正克重并明确确认后作用于整餐，不存在 `initialMealAllocationService` 或其他自动配比模块。

### 6.4 记录查询与详情

```text
首页最近一顿 / 记录页月份状态 / 详情页
  → sharedMealRecordService.list|get
  → sharedMealRecord(list|get)
  → shared_meal_records
```

列表使用 `mealTime DESC, _id DESC` 稳定游标。月份状态按上海自然月扫描分页结果，负责同月并发合并、缓存、旧响应失效、刷新和重试；日历模型负责上海自然日索引、打卡日期与选中日列表。

详情页只从记录快照建立 view model，不重新查询当前档案、目录、营养数据、标准或算法。记录没有 update/delete action。

### 6.5 主导航与页面职责

```text
首页       → homeStateModel 编排今日主任务、草稿、今日摘要和最近一顿
记录       → sharedMealRecordService 编排本餐月份、日期和详情入口
狗狗       → authService + dogService 编排档案列表与新增/编辑入口
我的       → authService 编排账号状态，不读取狗狗档案
中央记一顿 → sharedMealEntryService 统一进入 shared-meal 分包流程
```

`custom-tab-bar` 只负责真实目的地的选中态和路由切换；中央动作没有选中态。四个一级页面预留 `with-tab-bar` 底部空间，任务型子页面不注册或重复渲染该导航。

## 7. 云函数职责

| 云函数 | 当前职责 | 当前主线状态 |
| --- | --- | --- |
| `login` | 获取微信身份并建立用户索引 | 当前使用 |
| `dogProfile` | 档案合同、CRUD、归属和字段校验 | 当前使用 |
| `searchHumanRecipes` | 按活动 `recipe_version` 分页搜索人饭投影 | 当前使用 |
| `getHumanRecipe` | 读取一道活动人饭菜谱及全部来源原料 | 当前使用 |
| `sharedMealRecord` | `save/list/get`、幂等、归属、策略复核和稳定分页 | 当前使用，已部署 |
| `weightRecord` | 体重测量 CRUD、稳定分页、当前体重事务同步和删除回退 | W1.2 代码已完成，等待 OW1 授权部署 |
| `saveCustomRecipe` | 保存旧自定义狗饭 | 兼容保留 |
| `saveMealPlan` | 保存旧批量制作清单 | 兼容保留 |

共享本餐客户端不直读 `shared_meal_records`，也不把人饭菜谱、犬食策略或记录保存拆成页面级数据库查询。

## 8. 数据与合同边界

### 8.1 本地状态

- `access_token`、`currentUser`：鉴权恢复。
- `dogsCache/v3`：狗狗档案缓存，旧版本显式拒绝。
- `sharedMealDraft/v1`：单狗本餐工作状态和可选菜单搜索会话。
- Mock 环境使用独立的 `mock*` key，不改变生产合同。
- `pendingMealPlans`、`checkedItems` 等只属于旧批量兼容模块，不参与共享本餐保存。

### 8.2 公共运行时投影

- `human_recipes`：内嵌来源顺序、映射组件、四态策略和版本的人饭查询快照。
- `ingredient_catalog`、`canine_ingredient_policies`：目录事实和策略事实；操作资格由规则模块派生。
- `food_nutrition_profiles`、`pet_nutrition_standards`、`nutrient_rankings`：双轴评估和富含营养素入口的数据来源。
- `data_releases`：活动与可回滚发布版本。

公共投影由离线 SQLite 主库和受控发布脚本生成。页面不得组合原始审核表或自行推断映射。

### 8.3 用户业务集合

- `users`：登录索引。
- `dogs`：`dogProfile/v3` 档案。
- `shared_meal_records`：单餐不可变快照，ACL 为 `ADMINONLY`。
- `weight_measurements`：体重测量历史，ACL 为 `ADMINONLY`；由 `weightRecord` 云函数管理，W1.2 代码已完成但尚未 OW1 部署。
- `customRecipes`、`mealPlans`：旧功能兼容数据，不属于当前本餐聚合。

### 8.4 机器合同

- `contracts/shared-meal/shared-meal-ingredient-v1.schema.json`：共享本餐食材唯一合同。
- `cloudfunctions/sharedMealRecord/schema/record.schema.json`：记录字段合同。
- `cloudfunctions/sharedMealRecord/schema/indexes.json`：幂等、全部记录和按狗查询索引。
- `cloudfunctions/sharedMealRecord/schema/access.json`：仅云函数访问。
- `contracts/shared-meal/deviation-closure-baseline-v1.json`：任务依赖、排除范围和 Figma 前置门禁。
- `contracts/weight/weight-measurement-v1.schema.json`：体重测量记录字段合同；W1.1/W1.2 已接入客户端和云函数代码。
- `contracts/weight/weight-measurement-write-v1.schema.json`：体重测量规范化写入字段合同。
- `cloudfunctions/weightRecord/schema/*`：体重存储 schema、索引和 `ADMINONLY` 权限合同。
- `contracts/care/care-record-v1.schema.json`：护理记录实体字段合同；C1.1 已冻结，尚未接入云端。
- `contracts/care/care-record-write-v1.schema.json`：护理规范化写入字段合同；C1.1 已冻结，尚未接入云端。

### 8.5 体重与护理领域合同

体重测量记录与护理记录使用独立写模型，均以单狗为归属边界；后续只有在查询和展示层才汇入统一记录时间轴。W1.1 的体重合同见 `docs/superpowers/specs/2026-08-04-weight-domain-and-data-contract.md`，C1.1 的护理合同见 `docs/superpowers/specs/2026-08-04-care-domain-and-data-contract.md`。

体重客户端 service、adapter、云函数和资源合同代码已完成，但尚未创建线上集合、索引、云函数或线上数据。体重当前值同步由 W1.2 云函数事务实现，不提前接入首页事项或统一记录时间轴；OW1 仍需授权。

## 9. 可靠性与安全

### 9.1 一致性

- `sharedMealIngredient/v1` 固定稳定身份、来源引用、克重和数据版本。
- 相同输入和版本生成相同指纹与评估，不使用随机数或网络 AI。
- 同一 `_openid + idempotencyKey` 只允许一条记录；同 key 异指纹拒绝。
- 云函数按当前活动数据重新复核来源食材，伪造客户端状态不能绕过。

### 9.2 失败恢复

- 草稿恢复、关闭和档案往返不会静默清除用户输入。
- 菜单首屏、分页和详情错误保持已选状态，可局部重试。
- 记录 service 将未部署、存储未就绪、未登录、无权限、网络和不存在分类为稳定错误。
- 体重写入不自动重试；网络错误才标记为可重试。
- 月份加载失败保留目标月份、选中日期和旧数据。
- 保存失败保留相同保存意图，重试不会重复创建记录。

### 9.3 权限

- 业务集合通过云函数上下文 `_openid` 隔离。
- `shared_meal_records` 客户端不可直读或直写。
- `weight_measurements` 客户端不可直读或直写；写入必须复核当前用户的狗狗归属。
- 页面传入的 `targetDogId`、record ID 和任何 user ID 都不构成授权依据。
- 公共投影客户端只读；原始安全策略审核字段不直接暴露给页面。

## 10. UI 与组件边界

- 设计 token 位于 `styles/tokens.wxss`。
- 基础视觉能力位于 `components/ui/*`，第三方适配位于 `components/vendor/*`。
- 页面不得直接使用 TDesign 标签；日历、Checkbox、Icon 和 Loading 由 vendor wrapper 收口。
- 共享本餐主要复用 `ui-button`、`ui-card`、`ui-tag`、`ui-notice`、`nutrition-assessment`、`recipe-menu-indicator` 和 `record-calendar`。
- UI 变更必须通过 `check:ui`，并按 Figma 同 viewport 完成真实视觉验收。

## 11. 兼容边界

旧公共狗饭食谱、制作周期、批量清单、自定义狗饭和历史数据至少保留一个迁移周期：

- 旧路由继续注册并可读取历史数据。
- 旧业务服务和云函数可以继续存在，但不能成为共享本餐依赖。
- 旧 `mealPlans` 不迁移为 `shared_meal_records`，两种快照语义保持隔离。
- `app.globalData.recipes/latestPlan` 和旧待同步清单仍服务兼容路径，不代表当前主架构。
- 删除旧代码、集合或历史数据需要独立迁移方案和明确授权。

## 13. 关键取舍

- 采用原生小程序加 CloudBase，换取快速交付和微信身份集成；代价是当前后端实现与 CloudBase API 绑定，因此通过 adapter 和业务 DTO 控制耦合面。
- 采用本地草稿加云端不可变记录，换取返回恢复和简单历史语义；代价是草稿不能跨设备同步。
- 采用生成式跨分包复用，换取主包体积和分包独立性；代价是必须依赖同步脚本和漂移门禁。
