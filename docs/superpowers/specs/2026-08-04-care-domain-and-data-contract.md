## 1. 目标与边界

本合同只冻结护理领域的词汇、护理记录字段、用户填写的下次日期语义和单狗隔离规则，为后续 C1.2 提供稳定输入。它不创建 CloudBase 集合、索引、云函数或权限资源，也不改页面、首页事项、统一时间轴、线上数据或历史本餐快照。

机器可读实体合同为 [`care-record-v1.schema.json`](../../../contracts/care/care-record-v1.schema.json)，写入字段合同为 [`care-record-write-v1.schema.json`](../../../contracts/care/care-record-write-v1.schema.json)，纯合同参考实现为 [`careRecordContract.js`](../../../contracts/care/careRecordContract.js)。

## 2. 领域定义

### 护理记录

护理记录是用户为一只狗狗保存的一次护理事实。记录可以被编辑或删除，但删除后不恢复；编辑只修正同一条记录，不能把记录转移到另一只狗狗。

当前只允许四类：

| 稳定类型码 | 展示名称 | 语义边界 |
| --- | --- | --- |
| `vaccine` | 疫苗 | 用户记录已经发生的一次疫苗事实 |
| `internal_deworming` | 体内驱虫 | 用户记录已经发生的一次体内驱虫事实 |
| `external_deworming` | 体外驱虫 | 用户记录已经发生的一次体外驱虫事实 |
| `other` | 其他护理 | 不属于前三类的用户护理事实 |

类型码是跨客户端、服务和数据层的稳定值；中文名称只属于展示层，不能作为存储或筛选依据。

## 3. `careRecord/v1` 字段合同

保存后的实体固定为以下形状：

```json
{
  "schemaVersion": 1,
  "id": "care_001",
  "dogId": "dog_001",
  "type": "vaccine",
  "name": "狂犬病疫苗",
  "occurredOn": "2026-07-01",
  "nextDate": "2027-07-01",
  "notes": "社区动物医院",
  "createdAt": "2026-07-01T09:00:00.000Z",
  "updatedAt": "2026-07-01T09:00:00.000Z"
}
```

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `schemaVersion` | `1` | 是 | 固定合同版本，不能省略或降级写入 |
| `id` | 非空字符串 | 是 | 服务端生成的记录身份；客户端不能自定义 |
| `dogId` | 非空字符串 | 是 | 只属于当前用户拥有的狗狗；归属由服务端校验 |
| `type` | 四类类型码 | 是 | 只能使用上表中的稳定值 |
| `name` | 字符串 | 否 | 用户填写的名称；去除首尾空白，最多 120 个字符；未填写规范化为空字符串 |
| `occurredOn` | `YYYY-MM-DD` | 是 | 事实发生日期；按上海自然日解释，不能晚于写入当天 |
| `nextDate` | `YYYY-MM-DD` 或 `null` | 否 | 只有用户明确填写才保存；未填写规范化为 `null`，不能自动推导；不得早于 `occurredOn` |
| `notes` | 字符串 | 否 | 用户填写的事实备注；去除首尾空白，最多 2000 个字符；未填写规范化为空字符串 |
| `createdAt` | ISO datetime | 是 | 服务端创建时间 |
| `updatedAt` | ISO datetime | 是 | 服务端最后更新时间 |

日期字段是日期而不是时间戳，不携带时区和时间。这样可以避免在客户端、云函数和列表展示之间发生跨日偏移。时间字段只用于审计和同日排序，不改变护理事实的发生日期。

实体合同禁止额外字段。CloudBase 的 `_id`、`_openid` 等内部字段必须由服务端映射或隔离，不能泄漏成业务字段，也不能接受客户端传入 `userId`、`_openid` 来改变归属。

规范化写入字段的机器合同见 `care-record-write-v1.schema.json`。UI 可以省略 `name`、`nextDate`、`notes`，合同服务会分别规范化为空字符串、`null`、空字符串后再交给 C1.2。

## 4. 写入、读取与删除边界

这些是 C1.2 实现必须遵守的稳定接口语义，本轮不实现具体 adapter 或云函数：

| 操作 | 必需输入 | 结果与边界 |
| --- | --- | --- |
| 创建 | `dogId` + 全部规范化字段 | 服务端校验狗狗归属后创建一条记录 |
| 更新 | `recordId` + `type/name/occurredOn/nextDate/notes` | 只更新同一条记录的护理字段；`dogId` 不可变 |
| 删除 | `recordId` | 二次确认由页面负责；服务端删除后不恢复 |
| 列表 | `dogId`，可选 `type` | 只返回当前狗狗；默认类型为全部，分类筛选只接受四类类型码 |
| 详情 | `recordId` | 必须再次校验当前用户归属，不返回其他狗狗的记录 |

列表默认按 `occurredOn` 倒序；同一天使用服务端稳定记录标识作为第二排序键。分页、权限错误和网络失败由 C1.2 冻结，不得让页面直读集合。

## 5. 不可推导的边界

- `nextDate` 只是用户自己确定的计划日期。没有 `nextDate` 就不生成护理事项。
- 不根据护理类型、名称或发生日期推导周期、推荐日期、剂量、适用性或健康结论。
- `notes` 是事实备注，不作为疾病、过敏、用药或营养状态的结构化来源。
- 删除护理记录只影响护理列表及未来基于该条记录生成的事项，不影响体重记录、本餐记录或狗狗档案历史快照。
- 护理记录与体重测量记录、共享本餐记录保持独立写模型；后续统一时间轴只能在查询层汇合。

## 6. 版本与下游边界

- `careRecord/v1` 与 `careRecordWrite/v1` 是本轮冻结的稳定合同。新增字段或改变枚举语义必须升级版本，不在 v1 中静默复用旧字段。
- `contracts/care/careRecordContract.js` 是客户端和云函数未来共享的纯规范化/校验参考；本轮不把它接入主包、adapter 或页面。
- **C1.2：** 实现独立护理 service、adapter、云函数、集合 schema、索引、权限、分页、失败恢复和测试；不得自动部署云端资源。
- **C1.3：** 使用本合同实现护理列表、筛选、表单和删除确认；页面复用 D2.1 交接中的 UI Kernel，不在本合同中加入 UI 字段或医疗文案。
- **H2.1/R2.1：** 首页事项和统一记录时间轴属于后续任务，不由本合同提前改变。
