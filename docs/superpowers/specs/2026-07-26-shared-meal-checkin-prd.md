## 1. 交付目标

让用户每天从自己已经决定的人饭菜单中挑选可共用的基础食材，为一只符合适用条件的狗狗建立独立烹饪的本餐食材清单。系统提供本餐能量目标，但不生成缺少依据的单项克重；用户填写克重后，可按目标等比例缩放整餐，并通过现有能量与营养密度评估反复调整，最终保存一条可恢复、可追溯的本餐记录。

## 2. 目标用户

- 每天希望从既定人饭菜单中挑选基础食材，为狗狗单独无调味烹饪，并与狗狗在同一餐进食的普通养狗人。
- 狗狗档案完整、8 周以上，且没有疾病、妊娠、哺乳或治疗性体重管理需求。

不符合适用范围时不输出狗饭创建结果或伪精确数据。

## 3. 核心产品决定

1. 人饭由用户自行决定；产品不规划或推荐人当天吃什么。
2. 首版只使用既有菜谱库，不支持自定义人饭输入。
3. 非 `blocked` 食材可搜索、自动带入和添加；`blocked` 必须在客户端与云端共同阻断。
4. 系统只计算本餐能量目标，不自动填写食材克重或决定比例。
5. 用户填写初始克重后，可以按目标等比例调整整餐；食材组成继续由用户通过本餐评估调整。
6. 现有营养缺口和“挑选富含某营养素的食材”入口继续复用，不新增第二套推荐能力。
7. 首版只做单餐评估；历史快照为后续跨餐聚合留出余地，但不输出跨餐结论。
8. 营养不足不阻止保存；最高优先级偏高项或关键数据缺失触发一次确认。
9. 保存是一条本餐记录，不代表营养完整或适合长期重复喂养。

## 4. 核心流程

```text
首页发起
  → 登录与建档守卫
  → 选择本次狗狗
  → 搜索并选择已决定的人饭菜单
  → 查看全部来源原料与可共用状态
  → 自动带入非 blocked 食材
  → 查看本餐能量目标
  → 用户填写各食材初始克重
  → 可选：按目标等比例调整整餐
  → 查看能量与营养密度评估
  → 通过既有入口增删食材、调整克重并实时重算
  → 按结果分级提示
  → 保存本餐记录
  → 查看记录详情
```

## 5. 成功标准

完整、可切片的成功标准以机器契约中的 `successCriteria` 为准。人工评审重点如下：

- 用户可以从一只狗狗和至少一道既有菜谱开始，完成食材带入、克重填写、评估调整和保存。
- 产品不插手人饭决策，也不提供自定义人饭兜底。
- 单项克重必须由用户首次填写，系统只进行用户确认后的等比例缩放。
- 食材变化后双轴评估实时更新，现有富含营养素入口保持可用。
- 普通缺口不弹窗；最高优先级偏高项或关键数据缺失只确认一次；`blocked` 永远不能确认后继续。
- 草稿可恢复，保存幂等，历史记录保存完整快照和版本。
- 所有结论只针对本餐，不制造完整均衡或长期适用承诺。
- 新主导航为首页、记录、我的，旧批量制作主线在门禁满足后隐藏但暂不删除。

## 6. 明确不做

- 不决定或推荐人饭菜单。
- 不支持自定义人饭录入。
- 不自动生成食材克重、比例或用量上下限配置。
- 不自动补充食材、营养补充剂或长期配方。
- 不做连续多餐评估、趋势和长期完整性判断。
- 不支持疾病、妊娠、哺乳或治疗性体重管理方案。
- 不做计划/已食用双状态、历史记录编辑、社交、奖励或复杂统计；当天记录编辑由后续合同定义。
- 不在本轮删除旧代码和历史数据。

## 7. 交付约束

- 狗饭必须独立称量、独立烹饪，不继承人饭调味。
- 菜谱、目录、安全策略、营养来源、标准和算法均按版本读取和保存。
- 搜索、自动带入、额外添加与云端保存必须复用统一的非 `blocked` 规则。
- 复用现有能量、营养密度和本餐评估服务，不建立第二套公式。
- 不使用随机数、网络 AI 或不可追溯的生成结果。
- 数据新投影先进入 staging，完成数量、样本、阻断原因和回滚验证后才能激活。
- 新流程通过记录保存、草稿恢复、核心路径、UI 系统和包体检查后，才能隐藏旧主入口。

## 8. 责任边界

国标、FEDIAF 和其他营养档案只用于本餐估算参考，不能证明家庭自制单餐或长期饮食完整均衡。界面需要持续显示实际缺口、数据覆盖、标准版本和以下含义：

> 保存是记录本餐，不代表本餐营养完整或适合长期重复喂养。若家庭自制餐长期占主要饮食，请咨询兽医或宠物营养专业人士。
