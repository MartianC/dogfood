# 食谱模块 Figma 界面设计实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: 使用 `superpowers:executing-plans` 逐任务执行本计划；所有 Figma 操作必须按本计划加载对应的 `figma` skills。步骤使用复选框（`- [ ]`）追踪。

**Goal：** 在 Figma 中产出一套可交付的小程序“食谱”新模块设计稿，替换现有第二个 Tab 的公共食谱列表，支持用户管理自定义食谱、创建食谱、搜索添加食材并通过可伸缩营养抽屉查看汇总。

**Architecture：** 保持小程序四项底部导航，第二个 Tab 的名称仍为“食谱”，但内容改为“我的食谱”入口；原公共食谱列表和详情流程在本次设计中暂时隐藏、不删除、不再作为第二个 Tab 的主入口。设计稿以 TDesign 微信小程序组件的交互范式为基础，先复用 Figma 文件已有的设计系统资源；无可用资源时，再创建少量项目业务组件与语义 token。

**Tech Stack：** Figma Design、Figma MCP、`figma-create-new-file`、`figma-use`、`figma-generate-design`、`figma-generate-library`、TDesign 微信小程序组件库、微信小程序 375×812 逻辑画布。

> **执行边界：** 必须使用 Figma MCP 与 `figma` 技能完成本计划；不要在本计划阶段修改小程序代码、`app.json`、现有页面或云函数。

## 全局约束

- 所有页面、组件、状态和标注文案使用中文；营养单位使用 `g`、`mg`、`kcal`，不使用未经定义的缩写。
- 新设计必须遵循当前项目的设计语义：克制、生活化、易读、适合移动端单手操作；不使用诊断式或保证效果的营养文案。
- 第二个底部 Tab 保持名称“食谱”，其内容改为用户的自定义食谱列表；旧的公共食谱列表与详情页只在实现阶段保留代码，Figma 主流程不展示其入口。
- 设计范围仅覆盖“食谱”新模块及其与 Dock 的关系；首页、饮食计划（原“清单”）、我的页面不重做。
- 设计优先映射到 TDesign 微信小程序已有模式：`TabBar`、`Button`、`Cell`、`Search`、`Input`、`Popup`、`Stepper`、`Dialog`、`Empty`、`Loading`；开发实现时第三方组件需经项目 `components/vendor/*` 或 `components/ui/*` 适配层接入，页面不可直接耦合第三方标签。
- 可点击区域在设计标注中不得小于 44×44pt（对应项目中不低于约 88rpx 的要求）；固定底部控件必须预留安全区。
- 先搜索并复用当前 Figma 文件订阅的库、变量、样式和组件；没有匹配项才创建新的项目组件或变量。
- 所有 Figma 写入操作必须小步执行、每一步后验证；不得一次性生成整套复杂画布后不检查。
- 不创建 Git 提交、不执行 Git 暂存；本计划仅产生 Figma 设计稿与设计交接文档。

## 设计范围与用户主路径

### 信息架构

```text
Dock（首页｜食谱｜清单｜我的）
             │
             ▼
       食谱：我的食谱列表
        ├─ 新建食谱
        │   └─ 基础信息 → 食谱设计页
        └─ 点击已有食谱 ───→ 食谱设计页
                                ├─ 搜索食材
                                ├─ 输入克重并添加
                                └─ 展开营养汇总抽屉
```

### 必须呈现的状态

1. 食谱列表：有数据、首次使用空状态、加载中、删除确认。
2. 基础信息：默认、必填项校验失败、保存中。
3. 食谱设计：无食材、已有食材、食材行编辑、保存中、保存失败提示。
4. 食材搜索：默认、搜索结果、无结果、重复添加提示、克重为空/非法。
5. 营养抽屉：收起、半展开/展开、数据不足、营养偏低、适中、偏高。

### 首版营养展示规则

- 收起态只展示总重量、能量和一个概览性状态；不能假装提供完整诊断。
- 展开态优先展示：能量、蛋白质、脂肪、碳水、钙、磷、钙磷比。
- 每条营养项使用“当前含量 / 参考目标 / 占比”三层信息，其中无参考目标时明确标为“暂无参考值”，不显示伪精确百分比。
- 颜色不是唯一信息载体：偏低、适中、偏高必须同时有中文文字和图形/数值提示。
- 设计只定义信息呈现与状态，不定义医学判断；页面保留简短提示“营养数据仅供配方参考，如有健康问题请咨询兽医”。

## Task 3：设计“食谱”Tab 与食谱列表首页

**输出：** 新的第二个 Tab 及“我的食谱”列表主页面，包括数据态、空状态和删除确认。

**参考现状：**
- 现有 Tab 定义：`app.json`
- 当前被替换的页面入口：`pages/recipes/list/index`
- 现有公共食谱详情：`pages/recipes/detail/index`

- [x] **Step 1：制作 F01 Dock 状态。**

  使用 TDesign TabBar/Dock 模式设计 4 项底部导航：`首页`、`食谱`、`清单`、`我的`。`食谱`必须为已选中态；不增加第五个 Tab，不显示旧公共食谱入口。标注固定底部安全区与图标/文字的选中、未选中状态。

- [x] **Step 2：制作 F02 有数据列表。**

  标题使用“我的食谱”，辅以简短说明“记录常做的搭配，随时调整食材和份量”。放置至少 3 张代表不同状态的食谱卡片：已完成食谱、草稿食谱、长名称食谱。卡片信息至少包括名称、适用狗狗或未指定、食材数量、总克重与最近编辑时间；卡片点击区域进入食谱设计页。

- [x] **Step 3：定义新建入口。**

  在列表页放置单一明确的主要操作“新建食谱”。可使用固定底部按钮或页面内首要按钮；若固定底部，应与 Dock 的空间关系清晰，不能遮挡最后一张食谱卡片。

- [x] **Step 4：制作 F03 空状态与 F11 删除确认。**

  空状态文案应解释价值并把“新建食谱”作为唯一主操作。删除确认使用破坏性二次确认，说明删除后不可恢复；默认焦点放在“取消”，避免误删。

- [x] **Step 5：建立原型连线。**

  从 Dock 的“食谱”进入 F02/F03；从“新建食谱”进入 F04；从食谱卡片进入 F06；从删除操作进入 F11 删除确认。

**验收：** 评审者能明确看到第二个 Tab 已更换为用户食谱主页，且不会误以为旧公共食谱仍是该 Tab 的内容。

## Task 4：设计创建与食谱编辑主流程

**输出：** 从基础信息到编辑食谱、添加食材并修改克重的连贯主路径。

**参考现状：**
- 既有自定义食谱编辑页：`subpackages/custom-recipe/edit/index.wxml`
- 既有自定义食谱服务：`subpackages/custom-recipe/services/customRecipeService.js`
- 既有食材编辑组件：`components/ingredient-editor/*`

- [x] **Step 1：制作 F04 基础信息表单。**

  字段固定为：食谱名称（必填）、适用狗狗（可选选择器）、备注（可选多行输入）。主按钮为“开始设计食谱”；名称为空时展示内联错误“请填写食谱名称”，不以 toast 替代字段错误。将保存中状态设计为按钮禁用且有加载反馈。

- [x] **Step 2：制作 F05 空食材编辑页。**

  顶部包含返回、食谱名称和保存状态。页面主体解释“先添加食材，再查看营养汇总”，唯一主要操作为“添加食材”。底部放置收起态的 `NutritionDrawer`，在无食材时说明“添加食材后显示营养汇总”。

- [x] **Step 3：制作 F06 已添加食材编辑页。**

  每个 `IngredientRow` 展示食材名称、克重、单位和简要操作。克重可通过行内编辑或弹层编辑，但同一流程中只能采用一种交互模式；删除必须有可发现的入口且不得与编辑操作冲突。页面应支持继续“添加食材”，并展示至少 4 个食材以验证长列表与抽屉共存。

- [x] **Step 4：制作 F07 搜索食材。**

  使用顶部搜索框，初始态展示“最近添加”或“常用食材”；搜索结果展示名称、类别/来源与每 100g 的关键营养摘要。无结果状态必须提供“换个关键词试试”，不能虚构食材或提交自由文本。

- [x] **Step 5：制作 F08 克重输入弹层。**

  选中食材后以 Popup/底部弹层展示食材名称、每 100g 营养摘要、克重输入框和步进控件。主按钮固定为“添加到食谱”；克重为空、0、负数或超出合理上限时禁止提交并给出字段级原因。重复食材默认采用“合并到现有食材”的提示与确认，而不是静默创建重复行。

- [x] **Step 6：建立原型连线。**

  连线必须覆盖：F04 → F05，F05/F06 → F07 → F08 → F06，以及 F06 中修改克重、删除、继续添加的往返路径。

**验收：** 不阅读注释也能完成“创建食谱 → 添加两种食材 → 输入克重 → 回到已添加食材列表”的原型体验；所有输入错误至少在一个 Frame 中被具体展示。

## Task 5：设计并验证可伸缩营养抽屉

**输出：** 与食谱设计页面共存、不会遮挡主操作的固定底部营养汇总抽屉。

**接口语义：**
- 输入：已添加食材及各食材克重。
- 输出：总克重、关键营养素的当前含量、参考目标（如有）与比例/状态。
- 边界：没有食材、个别食材营养缺失、没有参考目标、数值偏低、适中、偏高。

- [x] **Step 1：制作 F09 收起态。**

  抽屉顶部带可点击/拖拽的把手；内容包含总克重、能量（kcal）与状态概览。默认高度只占用必要空间，且不遮挡“添加食材”入口或列表末项。给出“上拉查看营养汇总”的明确操作提示。

- [x] **Step 2：制作 F10 展开态。**

  以清晰分组展示能量、蛋白质、脂肪、碳水、钙、磷、钙磷比。每项使用 `NutritionMetric`，包含当前值、参考值（若有）、比例和文字状态。展开后抽屉内部可滚动，页面主体不可出现双重难以理解的滚动区域。

- [x] **Step 3：制作数据不足和阈值反馈。**

  在 F11 展示：数据不足时不计算比例、偏低/适中/偏高的文案与图形差异、钙磷比无法计算时的解释。状态颜色必须与文字和图标配合；禁用/不可用状态不能被误认为“健康”。

- [x] **Step 4：定义交互规格。**

  在 F12 标注：点击把手或摘要可展开/收起；拖拽是可选增强，不作为首版唯一操作；食材或克重改变后摘要应即时刷新；抽屉展开时仍能关闭且可返回编辑食材。

- [x] **Step 5：检查安全区与可达性。**

  在 375×812 及较短屏幕变体中检查：抽屉收起/展开时均不遮挡 Dock、系统手势区、主按钮、克重确认按钮；文字对比和字号满足阅读需要。

**验收：** 抽屉有明确收起和展开状态，营养计算未知时不会展示误导性的百分比，且设计可直接映射到 TDesign Popup/Drawer 类模式。
