# 微信开发者工具代码质量扫描修复记录

## 背景

微信开发者工具代码质量扫描不通过。排查时只执行本地编译和质量扫描，未上传代码、未生成预览二维码、未做真机调试。

## 扫描失败项

1. 主包存在主包未使用 JS：
   - `services/customRecipeService.js`
   - `services/fileService.js`
   - `services/planCalculatorService.js`
   - `services/recipeAdviceService.js`
   - `utils/auth.js`
2. 代码包未启用组件按需注入。
3. 图片和音频资源超过开发者工具质量扫描阈值。
4. 已提前修复并保留的项：`pages/home/index.json` 和 `pages/profile/index/index.json` 中存在未使用组件声明；根目录非运行文件需要通过 `packOptions.ignore` 排除。

## 根因

1. 根 `services/` 中有多份服务只被分包页面引用。微信开发者工具按文件所在包判断主包资源时，会把这类根目录服务判定为“主包未使用 JS”。
2. `utils/auth.js` 只服务自定义食谱编辑页，放在根 `utils/` 会被主包扫描命中。
3. `app.json` 缺少 `lazyCodeLoading: "requiredComponents"`。
4. 实际打包图片虽然单文件接近 200K 阈值，但开发者工具质量项对图片资源更保守。压缩前 `assets` 图片总量约 906K，扫描仍失败。
5. `.design-check/` 是本地界面检查截图目录，不属于小程序运行资源；该目录已在 `.gitignore` 和 `packOptions.ignore` 中排除，本轮按要求删除其中截图。

## 修复内容

1. 在 `app.json` 增加 `lazyCodeLoading: "requiredComponents"`。
2. 移除根目录只被分包使用的服务文件，将服务下沉到对应分包：
   - `subpackages/custom-recipe/services/customRecipeService.js`
   - `subpackages/custom-recipe/services/recipeAdviceService.js`
   - `subpackages/dog-profile/services/fileService.js`
   - `subpackages/plan-extra/services/customRecipeService.js`
   - `subpackages/plan-extra/services/planCalculatorService.js`
3. 删除根 `utils/auth.js`，在自定义食谱编辑页保留页面内 `requireProfileAuth()` 守卫逻辑。
4. 压缩小程序实际打包图片，`assets` 图片总量降至约 146K。
5. 删除 `.design-check/` 中的临时检查截图，并在 `AGENTS.md` 中补充检查截图清理要求。
6. 更新 `小程序架构设计.md`，同步当前服务层位置、分包边界和登录守卫写法。
7. 补充自动化测试：
   - `app.json` 启用组件按需注入。
   - 小程序图片资源不超过 200K。
   - 算法和建议服务测试改为引用分包内服务入口。

## 后续约定

1. 只在分包使用的页面服务优先放入对应分包，避免进入主包质量扫描。
2. 新增本地检查截图时放入 `.design-check/`，检查结束后删除。
3. 新增设计稿、测试、脚本或文档类文件时，同步评估是否需要加入 `packOptions.ignore`。

- 根因：运行时唯一调用者是 `subpackages/custom-recipe/ingredient-search`，但服务仍位于根 `services/`，因此按文件位置被归入主包。
- 修复：将服务移动到 `subpackages/custom-recipe/services/ingredientService.js`，搜索页改用同分包相对引用，并同步更新测试、`packOptions.include` 与架构文档。

## 2026-07-19 主包普通 JS 全量依赖检查

- 扫描现象：修复食材搜索服务后，质量面板继续提示 `data/options.js` 为主包未使用文件。
- 根因：档案选项只被 `subpackages/dog-profile` 使用，食材分类只被 `subpackages/custom-recipe` 使用；根组件 `ingredient-editor` 的引用不是主包真实页面入口，无法使 `data/options.js` 成为主包有效依赖。
- 修复：将档案受控选项移动到 `subpackages/dog-profile/data/options.js`；食材分类和旧编辑组件各自保留局部常量；删除混合在根文件中的已停用年龄阶段、过敏源等选项，避免跨分包共享文件进入主包。
- 全量检查：新增 `scripts/check-main-package-unused-js.js`，从 `app.js`、主包页面、已注册组件和自定义 TabBar 构建静态依赖图，对根 `config/data/services/utils` 的全部普通 JS 做可达性检查。修复前只检出 `data/options.js`，修复后返回“未发现主包未使用 JS”。
- 防回归：新增 `npm run check:main-package` 和 `tests/main-package-boundary.test.js`，后续新增仅分包使用的根 JS 时自动失败。
- 验证：全量测试 150/150、UI 检查、JS / JSON 语法与 `git diff --check` 通过；微信开发者工具 2.01.2510290 的 `build-npm` 成功，耗时 3439 ms，警告 0。代码质量面板仍需在开发者工具中手动点击“重新扫描”刷新结果。

## 2026-07-27 mainPackageReachability/v2

- 原因：`utils/ingredientOperationRules.js` 是 `custom-recipe` 与 `shared-meal` 的真实共享规则，旧检查器只从主包入口遍历，会误报为孤儿根 JS。
- 修复：检查器现在从 `app.js`、全部主包页面/组件及 `app.json` 注册的全部分包页面/组件入口遍历真实 `require` 图；只把实际入口可达的根模块视为使用中。
- 防伪：主包页面不为共享规则添加占位 `require`；正向 fixture 证明分包真实引用可达，反向 fixture 证明孤儿根 JS 仍失败。
- 验证：运行 `node --test tests/main-package-boundary.test.js` 与 `npm run check:main-package`。

## 2026-07-30 官方主包依赖语义修复

- 扫描现象：DevTools 继续报告 `services/draftAdapters/index.js`、两个评估入口、共享本餐资格判断和称量口径共 5 个“主包未使用 JS”；旧 `check:main-package` 因为从分包入口遍历而误报通过。
- 根因：DevTools 依据编译依赖图的直接父依赖判断；根目录 JS 即使被分包真实使用，只要没有主包父节点，仍属于该质量项。原生小程序不同分包之间不能同步 `require` 同一份分包 JS。
- 修复：单分包专用模块直接移动到实际分包；评估、共享草稿合同和食材操作规则迁入不打包的 `shared-src/subpackage-services` 唯一源码，再由无第三方依赖的同步脚本生成到 `custom-recipe` 与 `shared-meal`。页面只引用包内副本，未向 `app.js` 或主包页面添加占位依赖。
- 防回归：新增 `sync:subpackage-services` 与 `check:subpackage-services`，测试固定生成内容一致、两个分包模块状态隔离、`shared-src` 被 `packOptions.ignore` 排除，并使用 skill 内 `check:code-quality` 作为官方规则预检。
